# VERTEX Files — Product and Engineering Specification

Status: requirements baseline, not shipped. This document records the product direction and is the handoff for future implementation agents.

## Product and scope
Build a self-hosted file manager with cross-device access and construction document control. Start from the existing VERTEX Files design in this directory. Preserve its visual identity across web, macOS, Windows, iOS/iPadOS, and Android; adapt navigation and interaction to screen size and platform. Provide an installable path on each OS. An installable web app can validate the common experience first; native packages and desktop integration remain explicit deliverables. Track FileOS's advertised capabilities in a dated parity matrix, with original VERTEX UI. Include file operations, multi-pane browsing, favorites, workspaces, quick preview, content search, cleanup, duplicate detection, previews and undo, and developer/agent views. Keep AIDE, MSP-BI and Messenger outside this implementation scope.

## 1. Server and connectivity
The owner's 5 TB storage is the authoritative file store. Run the service and background workers on the storage server if supported, or on a dedicated always-on computer with controlled access to its mounted storage. In the latter topology client access depends on that computer being online. Verify OS, filesystem/share protocol, available compute, permissions, and backup capacity before selecting the runtime. Use one authenticated API for all devices. Support LAN/Wi-Fi and remote HTTPS through an approved private-access or gateway configuration. Do not expose the file share directly to the internet. Enforce project roles and path containment on the server. Sharing links require authentication and explicit access to the referenced item or version; support expiry and revocation. Keep account identity and storage paths under server control. Use resumable uploads, checksums and atomic finalization; test interruption and low-disk behavior. Keep backups separate from primary storage and test restore.

## 2. Projects and automated intake
Model Project, ManagedFolder, Document, DocumentVersion, IntakeItem, Share and AuditEvent as stable entities. Define a construction project template with drawings, renders, permits, correspondence, municipal correspondence and procurement/purchase orders. Use Aqeeq 3 (عقیق ۳) as the reference project. Create folders when the project/template is configured. Every upload enters a managed inbox first and receives a durable receipt. Extract PDF text and use local Persian/English OCR for scans. Classify project, document type and destination using file metadata, content and project vocabulary with local AI on owner-controlled infrastructure. Store original filename, suggested title, short description, classification provenance and confidence. Apply permitted naming and placement automatically above a configurable confidence threshold; send ambiguities to review. Retain the original bytes, prevent overwrites, allow authorized reversals, and make retries idempotent. Verify with a municipal letter, a purchase order, a render and an ambiguous scan.

## 3. Drawings, versions and sharing
Use a stable drawing ID independent of filename or folder. A completed save with changed bytes creates an immutable version with sequence number, hash, server time, actor ID and base version. Same-content saves do not create extra versions. Desktop integration must report complete saves from managed AutoCAD sessions; ignore temporary files and avoid snapshotting partial writes. Attribute uploads, saves and shares to the authenticated account that performed each operation. Handle concurrent edits by detecting stale base versions and preserving both changes for review. Keep latest working version and latest approved-for-construction version separately addressable. Tie approvals to an immutable version. A Tehran-to-Isfahan share pins a version; record recipient, share time and view/download activity. Example: Danial uploads S-104 v07, an Isfahan colleague opens and saves v08 under their account, and a third user shares v08. Opening or closing alone produces audit events, not new versions.

## 4. Black box audit trail
Persist an append-only server-side audit journal for managed open, close, preview, download, upload received/completed, edit and version save, share sent/received, rename, move, classification, approval and restore. Record event ID, correlation ID, server UTC timestamp, authenticated actor or system identity, project/document/version IDs, action, result and applicable before/after names, locations or recipient. Define received as observed delivery to the application's inbox; record recipient opening and downloading as separate events. Use authenticated client signals for managed editor opens/closes, and mark their provenance; downloads opened externally cannot be observed. Do not fabricate close events after client crashes. Couple mutation events with the operation using a transactional write or durable outbox with deduplication. Provide a timeline and filters by actor, project, document, action and date, with access-controlled reporting. Ordinary users cannot edit history. Protect log storage and backups and define retention before production.

## 5. Implementation order and acceptance
1. Review the current Files UI and hosting constraints. Sketch the same Aqeeq 3 workflow for web, macOS, Windows, iOS/iPadOS and Android. Document platform installation and native integration needs.
2. Build an isolated vertical slice with sample storage and test accounts: create Aqeeq 3, upload a PDF from a mobile browser, authorize download from a second account, and verify the audit timeline. Verify an unauthorized account cannot read it.
3. Add inbox extraction, local OCR, classification, placement and review with the fixtures above. Verify retries, reversal and preservation of source content.
4. Add version history, review/approval, pinned links and the desktop save adapter. Verify attribution and concurrent save behavior using the Tehran–Isfahan example.
5. Validate cross-platform installation, desktop open/close reporting, backup/restore, and performance with representative large files. Expand the parity matrix feature by feature.

Record implementation status and evidence against each phase. The first build is the Aqeeq 3 vertical slice. Confirm production server topology, permitted remote access, identities, approval roles and local model capacity before deployment.
